Twelve laptops and a leaky cross-validation

November 2026 · Medrano Mercantile sales models

My price model had failed its gate on every run since I built it. Then I recorded one bulk sale, and it passed. A pass after one sale should have been suspicious on its own. Here's what was going on.

The setup

The model predicts an item's sale price from its category and name. Before any model counts, it has to beat a simple baseline (the median sale price) on repeated 5-fold cross-validation, with a 95% bootstrap interval on the improvement that excludes zero. I also score a holdout of the most recent 25% of sales, as a second check that respects time.

On 76 sales, nothing passed. The best model was about as good as the median, which is an honest answer for a small, messy dataset.

What changed

I sold part of an office cleanout to a local IT shop: twelve items for one lump sum, split across the items in proportion to their list prices. Nine of them were laptops of the same model, recorded as "Dell Inspiron 16 5630 i5 Laptop (Unit 1 of 5)", "(Unit 2 of 5)" and so on, at identical prices.

The next training run crashed, and the crash turned out to be the useful part. The random forest had passed the gate, which sent the code down its "register the model" path for the first time, and MLflow refused to save the model. Code that has never run tends to break the first time it does.

Why the pass wasn't real

Plain K-fold splits rows at random. With five identical laptops in the data, unit 1 lands in training and unit 2 lands in testing, so the model is graded on items it has effectively already seen, at prices it has already memorized. The forest, which can memorize a name, gained the most from that.

The time-ordered holdout disagreed with the cross-validation the whole time. On the most recent sales the forest's error was $69.30, worse than a ridge model's $52.34. When two honest checks disagree that much, the more flattering one is usually the one that's wrong.

The fix

Units of the same product now share a cross-validation group, so they always land on the same side of a split:

names = X["item_name"].str.replace(r"\s*\(Unit \d+ of \d+\)\s*$", "", regex=True)
folds = GroupKFold(5, shuffle=True, random_state=seed)
for train, test in folds.split(X, groups=names.str.lower()):
    ...

That cut the forest's apparent gain by more than a third, from $13.95 to $8.75. It still passes, and I don't think it should. The bootstrap still resamples individual sales, so nine near-identical laptops count as nine independent pieces of evidence. The model also still loses to ridge on the recent holdout.

What I'm taking from it

  • Identical units are real sales, so they stay in the data. They have to stay on one side of every split.
  • A sudden pass deserves more suspicion than a steady fail. One business event shouldn't flip a model's verdict.
  • A second check that can disagree is worth keeping. The time-ordered holdout said no all along.
  • Code paths that have never run will break the first time they do. The registration branch crashing is what made me look.

The next change is to resample by product in the bootstrap as well, and to require a model to beat the best alternative on the holdout too. Until then I treat the forest's price estimates as rough.
